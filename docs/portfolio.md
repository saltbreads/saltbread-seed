# Portfolio Case Study — Naver Map “Saltbread” Place Data Pipeline

## 1. Problem

대구 지역 “소금빵” 관련 매장 후보를 수작업으로 찾는 과정은 시간이 오래 걸리고(검색/정리 반복),  
매장별 정보 형식이 제각각이라(영업시간, 메뉴, 가격 표기 등) 팀 단위로 공유하기 어려웠습니다.

**목표**
- 후보 매장을 넓게 수집하고(리콜), 실무에 필요한 핵심 정보를 일관된 스키마로 정리
- 중단/재시작 가능한 대량 처리 파이프라인 구축
- 결과물을 팀원에게 최종 CSV로 전달 가능한 형태로 생산

---

## 2. Approach (End-to-End Flow)

### Step A. Seed generation via Official APIs (Search + Geocode)
- 키워드 조합(예: `대구 + (동/핫플/역세권) + 소금빵 + (카페/베이커리/맛집)`)을 체계적으로 구성
- 네이버 개발자 API를 사용해 매장 기본 정보(이름/주소 등)를 수집
- 지오코드 API로 좌표(mapx/mapy, lat/lon)를 함께 저장

**핵심 포인트**
- seed 단계는 “정식 API 루트” 기반으로 접근해 정당성과 재현성을 확보
- 캐시를 통해 중복된 호출을 제거하여 속도/쿼터 안정성 향상

---

### Step B. SID extraction via Search + Regex
- 매장명 기반으로 재검색(`대구 + {가게이름}`)
- 결과 URL에서 정규식을 사용해 Naver Place SID를 추출
  - 이후 모든 enrichment는 SID를 키로 동작

**이 단계에서의 제약**
- 이후 일부 구간은 자동화 접근이 제한(캡차 등)될 수 있어, 렌더링 기반 자동화로 전환이 필요

---

### Step C. Enrichment via Selenium (Public Business-friendly Info)
SID를 순회하면서 네이버 지도 페이지에서 공개 정보를 추출했습니다.

- 스크롤만으로 렌더되는 항목(클릭 불필요)
  - 전화번호
  - AI 브리핑
  - 방문자 리뷰 키워드
  - 대표(히어로) 이미지

- 클릭/토글 이후 가능한 항목(사용자 액션 필요)
  - 영업시간(토글 펼침 후 상세 블록 텍스트)
  - 메뉴 탭 → “펼쳐서 더보기”가 없을 때까지 반복 클릭
  - 메뉴명/가격/이미지 URL 전체 수집
  - 메뉴 이미지 Top5를 규칙 기반으로 선별

**데이터 윤리 관점**
- 블로그 글 전문 등 개인 창작물을 대량 수집하는 방식이 아니라,
- 매장 운영에 실질적으로 도움이 되는 정보(메뉴/가격/영업시간/공식 등록 사진 등) 중심으로 구조화했다는 점을 강조할 수 있습니다.

---

## 3. Key Design Decisions

### 3.1 확장성: “키워드만 바꾸면 재사용 가능한 파이프라인”
앞쪽 검색 쿼리 구성만 바꾸면,
- 지역(대구→다른 시/구)
- 카테고리(소금빵→다른 디저트/메뉴)
로 동일한 파이프라인을 재사용할 수 있도록 설계했습니다.

### 3.2 안정성: Checkpoint + Status-driven Pending
대량 처리에서 중요한 것은 “실패를 관리 가능한 형태로 만드는 것”이었습니다.

- Checkpoint CSV 저장으로 중단/재시작 가능
- status 코드로 실패를 유형화해, 재시도 가치가 있는 실패만 다시 수행
- 타임아웃/스크롤/지터 sleep으로 렌더링 편차 흡수

예시 status:
- `OK`
- `*_NOT_FOUND` (섹션 자체 없음/미등록)
- `*_NO_DETAIL` (토글은 있으나 상세 없음)
- `*_ERR:ExceptionName` (예외 유형 기록)

### 3.3 메뉴 이미지 우선순위 규칙
실무적으로 “소금빵 관련 이미지가 있는지”가 핵심이었기 때문에,  
정확 일치 → 부분 포함(시오/소금빵) → 유사 키워드(솔트/버터롤) → 빵 일반 → 등록 순서  
순으로 Top5를 선별했습니다.

## 4. Implementation Notes

### Foldering Rationale
- `scripts/`: 실행 단위(엔트리 포인트, I/O, pending 조건)
- `src/clients/`: 네이버 지도/웹드라이버 접근 모듈 (셀렉터/추출 함수)
- `src/utils/`: 스크롤/대기/공용 함수 (재사용/테스트 용이)
- `data/`: 산출물 분리 (코드와 결과물의 변경 주기 분리)

### Testing → Production Methodology
- 초기에는 TEST_LIMIT로 소량 테스트(10~30)로 실패 케이스를 빠르게 발견
- status/debug 로그를 기반으로 엣지 케이스 보강
- 안정화 후 전체 후보에 대해 대량 실행

## 6. Limitations & Future Improvements

- 네이버 지도 UI/클래스 변경에 취약 → 셀렉터 안정화 전략 필요
  - 텍스트 앵커 기반 탐색 강화
  - 구조 변화에 대비한 fallback 체계 강화
- 캡차/차단 정책 강화 시 대응 필요
  - 요청 빈도 제어, headless 안정화, Playwright 전환 검토
- 데이터 품질 개선
  - 가격 표기(변동/문의) 정규화
  - 메뉴 카테고리 분류(빵/음료 등) 추가
  - 중복 메뉴/중복 이미지 제거 개선

---

## 7. What I Learned

- “대량 수집”은 추출 로직보다 **실패/재시도/중단 복구 설계**가 품질을 좌우
- status 설계와 checkpoint가 있으면, 실패가 “장애”가 아니라 “관리 가능한 상태”가 됨
- 확장 가능한 파이프라인은 앞단(seed)과 뒷단(enrich)의 결합을 느슨하게 만드는 것이 핵심
